# KAORI Website v0.1.4

This release makes the public KAORI Website's version information more trustworthy
and reduces the privileges available to its running web container. The Website
keeps its familiar design and public addresses while tightening how signed
builds, stable releases and deployment evidence are distinguished.

## Highlights

The footer now separates the **original immutable Website build** from the
**verified stable release**. A release is identified as stable only when
independently committed deployment and publication records match the running
signed image. When that evidence is missing or outdated, the Website clearly
says that the stable release is not verified instead of guessing a version.

## Improvements

- Strengthens the static Website's container boundary by using a minimal,
  allowlisted build context and a smaller runtime content set.
- Runs the Website as a non-root user with all Linux capabilities dropped,
  privilege escalation disabled and a read-only root filesystem.
- Serves release-status metadata from a read-only, same-origin location.
  Signed build identity remains visible without requiring visitors to query
  GitHub or the container registry directly.
- Preserves the existing single public Website at `https://kaori.cloud` and
  its reviewed, digest-pinned release and recovery process.

## Fixes

- Prevents an immutable release-candidate build label from being mistaken for
  an already published stable version.
- Ensures that a new release candidate, rollback or mismatched release record
  cannot incorrectly inherit the stable status of a different signed image.
- Improves release-contract and browser regression coverage for missing,
  invalid and inconsistent version metadata.
- Restores reliable signed release-candidate selection and browser evidence
  for the reviewed release workflow.

## Known Limitations

- The public Website introduces KAORI; it is not the authenticated KAORI
  Application or a live infrastructure operations dashboard.
- The build footer retains its original signed release-candidate identifier
  after stable publication. This is intentional: the stable version and build
  provenance describe different facts.
- The public Website uses the currently approved shared deployment runtime.
  Separate GitHub governance Environments do not themselves provision
  separate servers or public UAT domains.
- Non-root and zero-capability NGINX do not establish that the host Docker
  daemon is rootless. Host security, rollback evidence and protected release
  approval remain separate operational controls.
- Stable release publication requires accepted public UAT, a reviewed source
  promotion and explicit protected production approval; a signed candidate or
  green CI run alone is not a stable release.
